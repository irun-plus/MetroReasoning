# MetroReasoning V1物理环境代码设计说明

## 1. 目标与范围

V1先完成可复现的列车—乘客物理状态转移，为后续优化算法提供稳定接口。本版仅模拟单方向、单区间、完全封锁；不把多区间、双方向、降级通行或复杂客流控制提前混入。

决策间隔固定为300秒，仿真采用事件驱动：每个决策窗口内，时钟跳转到实际发生的事件时刻并按固定优先级处理，而不是每秒扫描全线路。

## 2. 五个核心文件

| 文件 | 单一职责 | 主要接口 |
|---|---|---|
| `Constant.py` | 线路、站台、列车和折返设施参数 | `STATION_NAMES`、容量、运行时分、折返设施 |
| `configure.py` | 中断真值/观测边界、场景构造和抽样 | `Config`、`DisruptionTruth`、`sample_disruption`、`edge_occupancy` |
| `TrainOperator.py` | 列车动作类型、列车状态与局部动作校验 | `HoldingAction`、`DelayAction`、`TurnbackAction`、`ReleaseAction`、`TrainOperator` |
| `PassengerOperator.py` | 进站配额和乘客分配/上下车/清客规则 | `EntryControlAction`、`PassengerOperator` |
| `Env.py` | 统一状态、事件队列、跨模块协调、守恒和指标 | `Env.reset`、`Env.observe`、`Env.step`、`Env.metrics` |

`__init__.py`只负责导出接口，不属于第六个业务模块。ALNS不放在本次V1物理环境中。

## 3. 数据接口

`DataBase/beijing_5/train_schedule.npy`形状为`(149,23,5)`；每行记录列车在车站的到达、发车、方向、列车编号和车站编号。OD数据由上下行矩阵组成，原始数组形状均为`(7201,23,23)`，每60秒有一个需求时刻。V1加载时合并为`(7201,2,23,23)`，方向0下行、方向1上行。

`DataBase/beijing_5`及`down_flow_list.npy`、`up_flow_list.npy`保留原样；当前事件仿真直接读取`train_schedule.npy`和两份OD矩阵。

## 4. 中断与信息隔离

`DisruptionTruth`只由环境内部持有，包含实际持续时间。`observe()`生成`DisruptionObservation`，只公开预测结束时刻及当前可观测封锁状态，不公开实际结束时刻。优化器未来只能接收`Snapshot`和明确公开的配置，不得读取`Env._truth`。

场景抽样函数要求显式传入预测持续时间，预测值与抽样实际持续时间独立，避免把真实恢复时间泄漏给决策器。场景抽样先抽有向区间，再在该区间的无中断基础运行图可行时刻集合内抽取开始时刻。选定区间没有可行时刻时直接报错，不重抽其他区间，因此不会通过重抽悄悄改变区间分布。静态占用只服务仿真前抽样；运行期占用与事件状态由`Env`维护。

## 5. 列车动作与状态机

### 5.1 状态

`NOT_STARTED`、`RUNNING`、`DWELLING`、`READY_TO_DEPART`、`HELD`、`TURNING_BACK`、`OUT_OF_SERVICE`。`NOT_STARTED`用于承接时刻表中尚未到达首站的车次；`OUT_OF_SERVICE`表示当前运营任务结束，历史记录及`vehicle_id`仍保留。

### 5.2 动作

| 动作 | 生效条件 | 物理效果 |
|---|---|---|
| Holding | 当前站且`READY_TO_DEPART` | 取消待发事件，保持`HELD`，直到显式Release |
| Delay | 当前站且`DWELLING`或`READY_TO_DEPART` | 增加当前站计划发车时刻；不自动修复其他列车 |
| Short-turning | 当前站且`READY_TO_DEPART`，存在对应来车方向折返设施，站台可完整容纳清客乘客，资源空闲 | 清客、占用折返资源，进入`TURNING_BACK` |
| Release | 当前站且`HELD` | 解除扣车，转为`READY_TO_DEPART`并重排发车事件；不等于立即发车 |

动作作用域均为即时命令，不允许在未来车站预约动作。每列车每轮最多一个动作。`TurnbackAction`不接受目标方向，方向由`1-current_direction`确定。

### 5.3 折返作业

折返开始时刻为动作执行时刻；结束时刻为`start + turnaround_seconds`。资源按`resource_id`独占区间`[start,end)`。作业期间列车为`TURNING_BACK`，不可发车或再次Hold。折返完成事件独立发生于结束时刻，释放资源、翻转方向，并为同一`train_id`和`vehicle_id`生成反向后续运行任务。折返时长包含清客和折返作业总时间，避免另行重复计入清客时间。

### 5.4 Release重排

解除扣车后最早发车时刻为：

`max(当前时刻, 原计划发车时刻, 前车实际发车时刻+最小追踪间隔, 停站作业完成时刻, 折返完成时刻)`。

若区间仍封锁，发车事件被阻止并记录`blocked_departure`，列车保留待发状态，环境内部在真实开放时刻重新尝试；真实开放时刻不进入Snapshot。

## 6. 客流动作、位置和守恒

V1仅有`EntryControlAction`，限制一个决策窗口内某站某方向最多进站人数。站台容量是物理硬约束，进站限流是决策动作，两者分开实现。

乘客物理位置只有站外队列、站台和车内。`stranded_platform`只是站台乘客的逻辑状态标记，不能作为第四个空间；其人数已计入`platform`。折返清客前先检查站台完整容量，若容纳不了全部清客乘客，则折返动作整体不可行，不允许部分清客或转移到站外。故障解除时清除滞留标记，乘客仍留在原站台队列。

上行目的站按递减顺序分配，下行按递增顺序分配，避免方向偏序错误。每个事件处理后检查：

`arrivals_total = completed_total + outside.sum() + platform.sum() + onboard.sum()`。

## 7. 事件驱动与评价时域

同一时刻事件优先级固定；在300秒决策边界，先处理到站/下车、折返完成、故障解除、OD到达和停站作业完成，再生成观测并接受动作，最后处理同刻发车事件。具体顺序为：

1. 列车到站与正常下车；
2. 折返完成；
3. 故障解除及滞留标记恢复；
4. OD乘客到达；
5. 停站作业完成；
6. 进站配额/站台容量分配；
7. 上客与发车约束检查。

决策边界同刻发车事件会延后到动作校验/应用之后处理，使Holding、Delay、Turnback等即时动作可以作用于该边界待发列车。同刻OD到达先计入站外队列，但进站分配延后到本轮配额下达后执行，避免边界客流误用上一窗口的限流配额。

实现中进站分配在OD到达后立即执行，并在发车上客前再次执行，以覆盖没有同刻OD事件的发车时刻；同刻到站优先于OD到达，OD到达优先于上客/发车。

时间约束：`H_decision <= H_eval <= H_forecast`。当前配置默认300秒、1200秒、1200秒。物理环境只生成历史客流预测供决策观察；本版尚未实现候选评价Gold或目标函数。Oracle只能用于离线性能上界，不得作为可部署策略的监督标签。

## 8. 指标

环境输出等待人秒、车内人秒、窗口末等待人数、车内人数、滞留乘客人数、站台拥挤超预警人秒、站台峰值、已完成乘客、累计计划时刻偏移、封锁阻止发车次数和守恒差。`onboard_pax_sec`是车内乘客暴露量，不等同于车内额外延误；`accumulated_schedule_shift_sec`是累计时刻偏移，不冒称剩余晚点。目标函数、权重、尺度和Gold由后续算法阶段另行设计。

## 9. 已知边界

- 站台容量由面积和密度假设推导，部分站型方向容量沿用原项目简化。
- 列车容量1440人、最小追踪间隔70秒、区间/停站运行时分、折返候选站及折返作业时间仍需来源核查。
- 折返设施只是仿真候选，不等于现行联锁许可。
- 本版未建模道岔冲突、具体股道占用、区间内多车停车位置、乘客换乘和跨方向重路由。
- V1不包含跳停、取消、新增车底、反向占用封锁区间、单线双向运行等动作。

## 10. V1折返计时口径说明（实现边界）

当前代码将`TurnbackAction`被环境接受的决策时刻作为折返作业起点，资源占用持续`turnaround_seconds`。这是与“即时动作、仅对当前站待发列车下达命令”相匹配的可执行口径。此前讨论中曾出现“从列车到站时刻起计时”的表述；若严格采用到站时刻起算，则必须进一步规定：列车到站时是否已预授权折返、300秒决策间隔内如何在到站事件触发动作、以及尚未作出折返决定时是否提前占用折返资源。当前代码没有把折返时间回溯到到站时刻，不能把两种口径混为一谈。此项应在物理环境最终验收时单独确认。
